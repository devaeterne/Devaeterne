## 🧠 How I Think About Software

### Architecture

Good architecture should make a system easier to understand as it grows.

I focus on clear boundaries between business logic, application services, persistence, authentication, infrastructure, and integrations.

### Business Logic

The most important part of many applications is not the frontend.

It's accurately translating real business processes into software rules that remain understandable and maintainable.

### Data

A strong data model prevents entire categories of problems.

I prefer keeping data integrity as close to the database as possible through relational modeling, constraints, validation, and carefully designed relationships.

### Simplicity

Complex business requirements do not automatically require complicated software.

I try to introduce complexity only where the problem actually demands it.

### Automation

If a repetitive process can be modeled reliably, it can probably be automated.

Automation should reduce operational friction rather than create another system people need to maintain manually.

## 🧭 Architecture Over Hype

I enjoy learning new technologies, but I don't choose technologies because they're fashionable.

The right tool depends on the problem.

Sometimes that means a modern serverless architecture.

Sometimes it means a relational database, a straightforward backend, and boring infrastructure that works reliably for years.

Technology should serve the system — not become the system.
